# Plan du lifter ARM32 → C (CPU de Pikmin 3 Deluxe)

## Mesures (2026-10-19, Ghidra sur `main`, `scripts/ExportIsaStats.java` → `notes/arm32_isa.tsv`)
- **4 035 995 instructions, 100 % en mode ARM (A32), 0 en Thumb.** Contre-vérification sur l'ELF brut : 0 `BLX` à adresse immédiate (cette forme bascule toujours en Thumb). `sdk` et `subsdk0` restent à vérifier (pas encore analysés).
- 45 017 fonctions (liste Ghidra `notes/functions.tsv`), section de code `0x0..0x10fdd60` dans `work/elf/main.elf`.
- ~166 mnémoniques de base. Cœur : 3,79 M d'instructions ; VFP/NEON : 247 000 (6 %).
- Les plus fréquentes : `ldr` 966k, `str` 425k, `add` 391k, `mov/cpy` 550k, `cmp` 259k, `bl` 249k, `b<cond>` ~330k, `ldm/stm` ~145k, `movw/movt` 88k, `blx` (registre) 64k, `bx` 21k ; VFP : `vldr/vstr` 76k, `vmov` 31k, `vmul/vmla/vadd/vsub` ~62k, `vcmpe/vmrs` ~30k, `vcvt`, `vdiv`, `vsqrt` ; NEON : `vld1/vst1` 13k, `vzip`, `vext`…
- Quelques mnémoniques douteux (`cdp2` 2 251, `ldab`) : probablement des **données (pools de littéraux, tables de sauts) désassemblées par erreur** par Ghidra. Le lifter doit s'appuyer sur un flot de contrôle propre, pas sur un balayage linéaire aveugle.
- Code indirect : 23 943 `BX reg` (dont les `bx lr` = retours) et 65 310 `BLX reg` (appels indirects : vtables C++, callbacks).

## Architecture proposée (calquée sur `tools/ssbu-recomp/tools/lifter/recomp.py`, adaptée au 32 bits)
1. **Mémoire invitée :** réserver 4 Go d'espace d'adressage (`VirtualAlloc` en réserve) ; adresse invitée `a` (u32) → `membase + a`. Comme toute valeur 32 bits tombe dans la réserve, **aucun test de bornes** n'est nécessaire (un accès hors zone engagée = faute, comme sur la console). Image chargée à une base choisie (ex. `0x60000000`, celle de Ghidra), relocations `R_ARM_RELATIVE` appliquées au chargement.
2. **Contexte :** `r[16]`, drapeaux `N Z C V Q`, `GE[4]`, registres VFP/NEON `d[32]` (= `q[16]`, `s[32]`), `FPSCR`, TPIDRURO (TLS), moniteur exclusif (`ldrex/strex`).
3. **Une fonction C par fonction invitée** : `void f_<addr>(Ctx *c)`, une étiquette `L_<pc>:` par instruction, **exécution conditionnelle** → `if (COND) { … }`. Littéraux `ldr rX, [pc, #imm]` résolus à la compilation depuis l'image (avec relocations).
4. **Flot de contrôle :** `bl` → appel direct `f_xxx(c)` ; `bx lr` / `pop {…, pc}` / `ldm …, {pc}` → `return` ; `blx reg` / `bx reg` hors retour → `call_indirect(c, addr)` (table adresse → fonction) ; **tables de sauts** (`ldrls pc, [pc, rN, lsl #2]`, `add pc, pc, rN, lsl #2`) → `switch` interne, comme `L_dispatch` dans ssbu-recomp.
5. **Débuts de fonctions :** cibles de `bl`, pointeurs vers le code dans les relocations, symboles exportés, plus la liste Ghidra comme graine ; vérifier les écarts.
6. **Imports (612 : nn::*, libc, libm, libc++…)** : stubs PLT → handlers du runtime avec l'**ABI AAPCS 32 bits** (arguments r0–r3 puis pile, 64 bits en paire de registres alignée, flottants en `s0..`/`d0..` si hard-float : à confirmer sur un appel à `sinf`).
7. **Décodage :** plutôt que d'écrire un décodeur ARM à la main, s'appuyer sur **Capstone** (décodage A32 + VFP/NEON, opérandes structurés) et écrire nous-mêmes la **sémantique → C**. Moins de risque d'erreur d'encodage.
8. **Vérification :** tests différentiels avec **Unicorn** (même moteur de décodage que Capstone, émulation ARM) : pour chaque forme d'instruction, comparer l'état après le C généré et après Unicorn, sur des valeurs aléatoires et limites (c'est ce que fait ssbu-recomp sur 32 043 cas AArch64).
9. **SDK :** `sdk` et `subsdk0` sont aussi du code invité : soit les lifter de la même façon (comme le `sdklift` de ssbu-recomp), soit remplacer leurs fonctions exportées par des implémentations natives (nn::*).

## Étapes
1. Installer `capstone` et `unicorn` (paquets Python) - **téléchargement à valider**.
2. Prototype : lifter une dizaine de petites fonctions feuilles (arithmétique + `ldr/str` + conditions), compiler le C, comparer à Unicorn.
3. Étendre aux appels, `ldm/stm`, retours, tables de sauts ; mesurer la couverture sur les 45 017 fonctions (`cover`, comme ssbu-recomp).
4. VFP puis NEON.
5. Runtime minimal (chargeur, mémoire, imports en stubs qui tracent) pour atteindre `nninitStartup` et les constructeurs statiques, comme le `boot_trace.txt` de ssbu-recomp.

## Ordre de grandeur
Le lifter AArch64 de ssbu-recomp fait ~60 Ko de Python (`recomp.py`) plus des outils annexes. Un lifter A32 sans Thumb est d'une taille comparable ; la part la plus longue sera l'exactitude (drapeaux, décalages, VFP) et le runtime en 32 bits.

## Prototype (2026-10-19) - `src/lifter/`
- Outils : venv `tools/venv` (capstone 5.0.9, unicorn 2.1.4). `a32lift.py` (décodage A32 à la main, Capstone pour les commentaires), `a32rt.h` (contexte, conditions, décalages avec retenue, AddWithCarry, mémoire `MB + a`), `harness.c` (réserve 4 Go, charge les PT_LOAD de `main.elf`, exécute sous SEH), `difftest.py` (cas aléatoires, Unicorn d'abord, puis le C, comparaison).
- Sous-ensemble géré : traitement de données (16 ops, immédiat / décalage immédiat / décalage registre, formes S), MOVW/MOVT, MUL/MLA/[SU]MULL/[SU]MLAL, CLZ, [SU]XT[BH](A), [SU]BFX, BFI/BFC, LDR/STR/B/H/SB/SH/D (tous modes d'adressage sauf T), LDM/STM, B interne, retours (`bx lr`, `mov pc, lr`, `pop {…, pc}`), exécution conditionnelle.
- **Test différentiel sur 12 fonctions feuilles** (`work/lifter/leaves.json`) : **1 977 / 1 977 cas identiques** (graine 1, 200 cas/fonction) puis **9 889 / 9 889** (graine 7, 1 000 cas/fonction) ; registres r0–r14, NZCV et mémoire (scratch + pile) comparés. Les cas où Unicorn faute ou ne revient pas sont écartés (21 %).
- **Test du test** : en inversant volontairement la retenue de `awc`, 9 fonctions sur 12 échouent (744 / 1 977 OK) → le harnais détecte bien les erreurs.
- Couverture sur tout `main` (instructions des 44 417 fonctions Ghidra) : **84,7 % des instructions liftables**, mais seulement 2 451 fonctions entièrement (il manque surtout les appels). Instructions encore refusées : `bl` 235k, VFP/NEON 203k, `blx reg` 62k, espace inconditionnel (NEON `0xF…`, `pld`, `dmb`) 33k, `ldrex/strex/swp` (et voisins) 27k, sauts sortants (tail calls) 13k, `mrs/msr` 3k, divers < 3k.
- Prochaines étapes : (1) appels `bl`/`blx`/tail calls + `call_indirect` + stubs d'imports ; (2) VFP (scalaires `s/d`, `vmrs`, `vcvt`) ; (3) NEON ; (4) `ldrex/strex/dmb` ; (5) tables de sauts (`ldrls pc`, `add pc`).

## Appels (2026-10-19, suite)
- **Ajouts au lifter** : `bl` (LR = adresse de retour puis `f_<cible>(c)`), `blx reg` (`call_indirect`), `bx reg` hors `lr` (saut indirect terminal), sauts sortants = tail calls, chute dans la fonction suivante, **imports** via la PLT (596 stubs `0x10fb820..0x10fdd5c`, reliés aux symboles par `R_ARM_JUMP_SLOT` → `imp_call(c, index)`). Débuts de fonctions = liste Ghidra + toutes les cibles de `bl` (43 895). **Accessibilité** : seules les instructions atteignables depuis l'entrée sont liftées (les pools de littéraux ne sont plus pris pour du code).
- **Harnais** : `call_indirect` (recherche dichotomique dans la table des fonctions liftées ; adresse inconnue → statut 3, compté à part), `imp_call` avec une sémantique de test identique côté Unicorn (hook sur la PLT), `guest_unimpl` → statut 4.
- **Méthode de test corrigée en route** (deux vrais défauts du test, pas du lifter) : (1) les segments inscriptibles (`.data/.bss`) sont restaurés avant chaque cas des deux côtés (Unicorn exécutait aussi les cas écartés, qui écrivaient dans les globales) ; (2) le code et `.rodata` sont **en lecture seule** des deux côtés, comme sur la console (un cas pouvait sinon dépendre d'écritures d'un cas précédent dans ces zones). Entrées : zone scratch avec 37,5 % de pointeurs et 18,75 % de zéros ; profil « riche en pointeurs » (bit 1 de la graine) avec 62,5 % de pointeurs, 25 % de zéros et 6,25 % d'adresses de fonctions liftées (pour exercer les appels virtuels).
- **Résultat sur 12 fonctions non feuilles** (`work/lifter/nonleaves.json`, fermeture de **37 fonctions** liftées) : **4 021 / 4 021 cas identiques**. Sept fonctions bien couvertes (23 à 1 000 cas chacune) ; les appels indirects n'ont que 2–3 cas par fonction, et 3 fonctions (`0x374`, `0x7cac`, `0x7d50`) n'ont **aucun cas exploitable** avec des entrées aléatoires (chaînes de pointeurs trop profondes) : non testées.
- **Test du test** : LR volontairement faux (+4) → 266 cas en échec sur 3 fonctions (LR et pile différents), puis code restauré.
- **Couverture sur tout `main`** (code accessible seulement) : **93,0 % des instructions** (3 308 703 / 3 556 557), **58,6 % des fonctions entièrement liftables** (25 726 / 43 895). Restent : VFP/NEON 191k + 30k (NEON dans l'espace `0xF…` : `vld1/vst1/vzip/vext`…), **instructions ARMv8 en mode 32 bits** `ldab` 20,5k, `lda/stl/ldaex/stlex` ~2,8k, `ldrex/strex` 1,5k (acquire/release, atomiques), **tables de sauts** `add pc, pc, rN, lsl #2` ~600, `mrs/msr` 159.
- À noter pour Unicorn : les instructions ARMv8-A32 (`lda*`, `stl*`, `vsel`…) demandent un modèle de CPU ARMv8 dans Unicorn (le modèle par défaut est ARMv7) avant de pouvoir les tester.

## Petits trous (2026-10-19, suite) - acquire/release, exclusifs, tables de sauts
- **Unicorn en ARMv8** : `mu.ctl_set_cpu_model(UC_CPU_ARM_MAX)` (le modèle par défaut refusait `ldab`). Les instructions ARMv8 en mode 32 bits de `main` sont donc testables.
- **Lifté** : `lda/ldab/ldah`, `stl/stlb/stlh` (simples accès mémoire : un fil hôte par fil invité), `ldrex*/strex*` et `ldaex*/stlex*` (octet, demi-mot, mot, double mot ; moniteur exclusif dans `Ctx` : armé, adresse, valeur vue ; le store-exclusif réussit seulement si le moniteur est armé, l'adresse égale et la valeur inchangée, comme QEMU/Unicorn), `clrex`, `dmb/dsb/isb`, `pld`. Tests sur 3 000 à 5 800 cas par lot.
- **Tables de sauts** : le modèle initial (`add pc, pc, rM, lsl #2`) était faux - **0 occurrence** dans `main`. La forme réelle (clang) est `cmp rI,#K ; bhi défaut ; add rB,pc,#4 ; ldr rO,[rB,rI,lsl #2] ; add pc,rB,rO` suivie de K+1 offsets relatifs à la table. `jt_targets()` la reconnaît même avec instructions intercalées par l'ordonnanceur ; le nombre d'entrées = jusqu'à la première cible (sinon `cmp`+1). **644 tables reconnues sur 656** (taille médiane 7, max 898), toutes avec des cibles à l'intérieur de leur fonction ; 12 non reconnues. Le C généré est un `switch (rB + rO)` sur les adresses d'invité.
- **Résultats** : lot 1 (5 fonctions `lda*`, 5 `ldrex/strex`, 5 tables) **4 335 / 4 335** cas identiques ; lot 2 (5 tables pilotées par l'index, 5 `stl*`, 5 `ldaex/stlex`) **5 807 / 5 807**. Familles réellement exécutées dans les cas aboutis (lot 2) : tables 1 043, `lda` 3 339, `stl` 1 838, `ldaex/stlex` 4 676 ; exclusifs `ldrex/strex` 364 (lot 1).
- Limites : 5 fonctions n'ont aucun cas exploitable (entrées aléatoires insuffisantes) ; seules 5 tables sont exercées par les tests (sur 644) ; le comportement multi-cœur des exclusifs n'est pas testé (Unicorn est mono-cœur).
- **Tests du test (petits trous)** : (1) statut de `strex` inversé → le C boucle indéfiniment dans les boucles `ldrex/strex` (harnais bloqué, 1 500 s de CPU, tué à la main) : détecté, mais à protéger par un délai maximal dans le harnais lors d'une prochaine session ; (2) cible n°1 des tables de sauts décalée de 4 → 42 cas en échec sur 1 725 (2 fonctions), détecté. `a32lift.py` a été restauré après chaque essai (vérifié : version saine).
